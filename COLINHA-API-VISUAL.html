Fundamentos

A ordem para lembrar

Requisitos → projeto → banco → entidades → dados de teste → repository → DTO → service → controller → erros → validação → testes → segurança, se necessária.

Essa é uma ordem para organizar as peças. No TDD, o teste de cada comportamento vem antes da implementação daquele comportamento.

Faça uma funcionalidade completa por vez: por exemplo, listar cidades atravessando todas as camadas. Depois faça cadastro, atualização e exclusão. Isso ajuda a descobrir problemas cedo.

Fundamentos

Modelar as entidades

Checklist de uma entidade JPA:

  • @Entity e, se quiser controlar o nome da tabela, @Table.
  • @Id e estratégia de geração, como @GeneratedValue(strategy = GenerationType.IDENTITY).
  • Construtor sem argumentos public ou protected.
  • Tipos apropriados: Long para ID; LocalDate para uma data sem horário; BigDecimal para dinheiro.
  • Getters e os métodos necessários para alterar seu estado.
  • Mapeamento dos relacionamentos e restrições do banco.

Trechos que já existem neste projeto:

Antes de abrir: Trechos parciais em duas classes diferentes. Em Event, use ManyToOne e JoinColumn; em City, use OneToMany com mappedBy. Inclua os imports Jakarta e, em City, List e ArrayList.

Ver exemplo — Trechos do relacionamento City–Event

Para lembrar: city_id é a coluna no banco; mappedBy = "city" usa o nome do atributo Java de Event.

Não adicione CascadeType.ALL apenas para fazer um erro desaparecer. Se a regra proíbe excluir cidade com eventos, propagar a exclusão para os eventos muda a regra e pode apagar dados indevidamente.

Se usar Lombok, confira o construtor exigido pelo JPA. Evite gerar toString, equals e hashCode envolvendo todos os relacionamentos: isso pode provocar recursão ou carregamentos inesperados.

Com @Id nos campos, o JPA usa acesso por campo; getters/setters continuam úteis para o seu código, mas não são todos obrigatórios para persistência. Por padrão, @ManyToOne é EAGER e @OneToMany é LAZY; planeje a consulta para os dados que o DTO precisa em vez de transformar tudo em EAGER.

Ao manter associações bidirecionais em memória, atualize os dois lados quando necessário; quem determina a chave estrangeira neste mapeamento é Event.city. Fonte: Jakarta Persistence — entidades, acesso e relacionamentos.

Use @Service, dependências finais e injeção pelo construtor. O exemplo usa os contratos da seção 8 e o repository da seção 7:

Para criar: receber CityRequest, construir uma City sem ID, salvar e devolver a resposta. As transações ficam nos casos de uso; a validação HTTP é acionada pelo controller da seção 10.

Ver exemplo — Classe completa: CityService

Não copie o ID recebido no cadastro: nesse contrato, quem gera o ID é o banco.

Para atualizar um evento, o roteiro é:

  1. Buscar o evento pelo ID da URL; lançar exceção de recurso inexistente se não achar.
  2. Buscar a cidade informada em dto.getCityId(); tratar a ausência conforme o contrato definido.
  3. Copiar name, date e url do DTO para o evento encontrado.
  4. Associar a cidade com entity.setCity(city).
  5. Salvar e retornar new EventDTO(entity) dentro da transação.

O teste atual não define a resposta para uma cidade inexistente no update. Esse é um caso a especificar ao ampliar a API.

Atenção ao update: construir uma entidade nova com o ID da URL e chamar save não garante, por si só, o comportamento de 404 esperado.

Atenção à transação: importe org.springframework.transaction.annotation.Transactional. Use readOnly = true para consultas e @Transactional para escrita. No uso padrão por proxy, uma chamada de um método para outro dentro da mesma instância não cria uma nova fronteira transacional.

readOnly é uma indicação para a infraestrutura, não uma validação de regra de negócio que impeça toda escrita. Por padrão, RuntimeException e Error provocam rollback; checked exceptions precisam de política explícita, como rollbackFor, se esse for o comportamento desejado. A configuração global pode alterar esse padrão.

Para excluir com tratamento de integridade:

Antes de abrir: Roteiro conceitual, não código Java executável. Implemente em um método público de service com @Transactional. Busque a entidade ou lance erro; depois exclua e force o flush dentro do tratamento de integridade. Crie e mapeie as exceções citadas.

Ver exemplo — Pseudocódigo: excluir com integridade

As exceções de domínio acima precisam ser criadas, normalmente estendendo RuntimeException, e mapeadas no handler. O flush() dentro do try força o envio das operações pendentes e permite capturar ali violações verificadas pelo banco naquele momento; sem ele, o erro pode aparecer apenas no encerramento da transação. Restrições adiadas pelo banco até o commit ainda podem falhar depois do try. Depois de uma violação, lance a exceção e deixe a transação desfazer a operação.

Exemplo para usar com o service anterior:

Antes de abrir: Arquivo: controllers/CityController.java. Depende dos contratos da seção 8, de Validation e do service da seção 9. Receba CityRequest com @Valid; devolva CityResponse. Delegue a criação ao service e retorne status 201 com Location. A criação usa create nas duas camadas para manter o vocabulário consistente.

Ver exemplo — Classe completa: CityController
AnotaçãoDe onde vem a informação

O controller chama o service. A regra de atualizar um evento e resolver sua cidade fica no service. Em um DELETE bem-sucedido, use ResponseEntity.noContent().build(); em um PUT que devolve o resultado, ResponseEntity.ok(dto).

Fontes: RequestBody e conversão HTTP, HTTP — RFC 9110 e PATCH — RFC 5789.

Padronizar erros e validar entradas

Crie um handler com @RestControllerAdvice e métodos com @ExceptionHandler para traduzir exceções:

SituaçãoTratamento
Recurso solicitado não existeExceção de domínio → 404
Cidade possui eventosExceção de integridade traduzida → 400 neste desafio
DTO viola uma validaçãoMethodArgumentNotValidException → status e erros de campo definidos no contrato
JSON malformado ou tipo incompatível400

Um corpo de erro pode conter timestamp, status, error ou message, path e, quando necessário, uma lista de erros por campo. Use um formato consistente.

Em uma API nova, ProblemDetail é uma alternativa padronizada do Spring para erros HTTP; não é necessário adotá-lo para cumprir este desafio. Não devolva stack traces, SQL ou detalhes internos como mensagem pública.

Para adicionar validação:

  1. Adicionar o starter Validation compatível ao pom.xml.
  2. Anotar os campos do DTO de entrada com jakarta.validation.constraints.
  3. Usar @Valid @RequestBody no controller.
  4. Tratar os erros de validação no handler.

Lembretes:

  • @NotBlank: texto obrigatório, sem aceitar vazio ou só espaços.
  • @NotNull: valor obrigatório.
  • @NotEmpty: coleção/texto não nulo e não vazio.
  • @Size: limites de tamanho.
  • @Positive: valor maior que zero; combine com @NotNull se também for obrigatório.
  • Restrições do DTO e restrições do banco se complementam.
  • Não imponha uma regra só porque ela parece comum. Exemplo: exigir uma data futura faria os dados históricos deste desafio serem recusados.

@Size e @Positive aceitam null; combine com uma restrição de obrigatoriedade quando necessário. Para validar um DTO aninhado, use @Valid no campo correspondente e restrições próprias no DTO filho. @Valid faz a validação em cascata; não torna o objeto obrigatório sozinho.

No caso simples de @Valid @RequestBody, a falha costuma gerar MethodArgumentNotValidException e o MVC responde 400 por padrão. O 422 do DSCommerce é um mapeamento explícito do handler. Restrições diretamente em parâmetros de métodos também podem produzir HandlerMethodValidationException nas versões atuais.

Fontes: constraints Jakarta, Size, Valid, validação de RequestBody e erros com ProblemDetail.

De javax para jakarta

Java EE passou a se chamar Jakarta EE. Na transição para Jakarta EE 9, APIs como Persistence, Servlet e Validation mudaram de namespace:

Serializable: depende da finalidade e da versão da especificação

java.io.Serializable é uma interface marcadora usada pela serialização nativa do Java, que representa objetos em bytes. Ela não é necessária apenas para um DTO ser convertido em JSON.

Para classes de chave primária composta, a exigência mudou no Jakarta Persistence 3.2: elas deixaram de precisar implementar Serializable. Em versões anteriores da especificação, essa exigência existia. Portanto, não remova a interface de uma PK de um projeto antigo apenas por estar usando jakarta.

Confira a versão efetiva de Persistence/Hibernate nas dependências do projeto. A classe da chave continua precisando de equals e hashCode consistentes com seus campos. Se outra funcionalidade exigir serialização Java, a interface ainda pode ser necessária. Referências: mudanças do Persistence 3.2 e Serializable no Java.

Inversão de dependência, injeção e isolamento

Uma classe depender de outra não impede, por si só, um teste unitário. A dificuldade aparece quando ela cria ou fica presa a uma dependência real de banco, rede ou outro recurso externo.

O princípio da inversão de dependência orienta depender de abstrações. A injeção pelo construtor permite fornecer a implementação real na aplicação e uma implementação controlada, como um mock, no teste. Inversão de controle, injeção de dependência e inversão de dependência são conceitos relacionados, mas não sinônimos.

Exemplo: CityService recebe CityRepository no construtor. No teste unitário, o mock do repository dispensa subir Spring e H2.

Fonte: injeção de dependência e testabilidade no Spring.

Regras para os cenários

  • Independência: um teste não depende do resultado, dos dados alterados ou da ordem de outros testes.
  • Cenário único: cada teste cobre uma situação clara; sucesso, ID inexistente e integridade viram testes separados.
  • Lógica simples: prefira um fluxo linear, sem condicionais e loops que decidam o resultado esperado.
  • Assertivas suficientes: um cenário pode ter várias verificações, como status, ID e nome do mesmo retorno.
  • Previsibilidade: use dados fixos. Quando o código depende de horário, injete um Clock controlável; para aleatoriedade, controle a fonte ou os dados.
  • Preparação explícita: use @BeforeEach para a base comum e prepare o que for específico dentro do cenário.

Essas regras são orientações para manter o teste legível, não proibições do JUnit: testes parametrizados, por exemplo, são adequados para aplicar a mesma regra a várias entradas. Fontes: ciclo de vida, BeforeEach e testes parametrizados no JUnit, Clock para controlar o tempo e ciclo TDD descrito por Martin Fowler.

Roteiro de segurança e OAuth2 do DSCommerce

Esta etapa corresponde ao projeto com usuários e perfis. O Event City atual não exige implementar login para cumprir seus sete testes.

Autenticação verifica a identidade; autorização decide o acesso. Para uma API nova, avalie usar um provedor de identidade existente: proteger a API como Resource Server não exige implementar um Authorization Server dentro dela.

Ordem de implementação

  1. Modelo User–Role: criar entidades, relacionamento, repositories e seed; armazenar senhas codificadas conforme o encoder.
  2. Exceções e validação: adicionar Bean Validation, exceções de serviço e handler com respostas padronizadas.
  3. Dependências de segurança: adicionar Spring Security e o suporte OAuth2 compatível; definir quem emite tokens e quem protege a API.
  4. Configuração externa: preparar variáveis de ambiente e propriedades.
  5. Infraestrutura de autenticação: carregar usuário, senha e permissões; configurar password encoder e conversão das authorities do JWT.
  6. Authorization Server: registrar cliente e fluxos, configurar emissão/assinatura do token e autenticação do cliente.
  7. Resource Server: validar JWT, configurar acesso às rotas, CORS, política de CSRF e tratamento de erros.
  8. Fluxo de login: para aplicações novas, usar Authorization Code com PKCE conforme o tipo de cliente. O password grant customizado é apenas referência para compreender o projeto antigo.
  9. Funcionalidades: implementar autorização por perfil e por proprietário do recurso, conforme o caso; testar login e acessos permitidos/negados.

O que mudou no OAuth2

Materiais antigos usam a infraestrutura legada Spring Security OAuth. No ecossistema usado pelo Boot 3, a configuração passou a usar Spring Security para Resource Server/Client e Spring Authorization Server para o servidor de autorização.

Não basta trocar os imports das classes antigas. Registro de cliente, cadeias de filtros, geração de JWT e fluxos suportados precisam corresponder à nova infraestrutura.

Na linha Spring Security 7, os recursos de Authorization Server foram incorporados ao próprio Spring Security. O projeto DSCommerce local usa a organização da linha anterior; não transplante essa configuração para o Boot 4 sem seguir o guia da versão. Fonte: Authorization Server no Spring Security 7.

O grant_type=password das aulas depende da implementação customizada existente no DSCommerce; não surge apenas por adicionar a dependência. O mecanismo de extensão usa AuthenticationConverter e AuthenticationProvider registrados no endpoint de token. Referência: extensão de grant no Spring Authorization Server.

Para projetos novos: o RFC 9700, seção 2.4, determina que Resource Owner Password Credentials não seja usado. Use Authorization Code com PKCE para fluxos interativos apropriados; para comunicação de serviço sem usuário, avalie Client Credentials. Uma SPA não consegue manter um client-secret confidencial. Fontes: práticas de segurança OAuth2 do IETF e SPA com PKCE no Spring.

Em JWT assinado, o conteúdo não está necessariamente cifrado: não coloque senhas ou segredos nos claims. Valide assinatura, validade, emissor e audience conforme o contrato da API. O Spring mapeia scopes para authorities com prefixo SCOPE_ por padrão; roles em um claim customizado precisam de conversão apropriada.

No navegador, CORS deve permitir o preflight antes da autenticação; Postman não comprova essa configuração. CSRF depende de como o navegador envia credenciais, especialmente cookies, e não apenas de a aplicação se chamar “API REST”. Os erros dos filtros de segurança precisam de tratamento próprio, como entry point e access denied handler.

Teste credenciais ausentes/inválidas (401) e usuário autenticado sem permissão (403). Em implantação real, use HTTPS para trafegar credenciais e tokens.
